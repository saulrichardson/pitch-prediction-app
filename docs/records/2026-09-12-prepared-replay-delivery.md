# Prepared Replay Refactor And Delivery

- date: 2026-09-12
- status: deployed and verified in production; see the [release receipt](2026-09-12-production-release.md)
- supersedes: async timeline-start jobs and per-click inference in the active web product

## Context

The September 11 audit measured roughly eight seconds for Next, changing
predictions after Back/Next, lost progress after refresh, and a phone layout with
controls far below the comparison. Public model quotas could stop a replay
midstream. The owner authorized an extensive product, design, and engineering
refactor toward a decisive, low-friction experience.

## Decision

Deliver one complete prepared at-bat, 3–8 pitches, as the unit of the public
experience. Keep all real-model work in an operator publication path. Immutable
editions preserve predictions; a small workspace-scoped cursor tracks progress.
One conditional write is the only durable change a replay command makes.

This changes the product from full-game stepping to a short complete replay.
It removes inference waits and mid-replay model quotas structurally. It does not
claim improved model accuracy or offline availability of unrevealed actuals.
No new service, queue, daily scheduler, or standing infrastructure cost is added.

The visual system is restrained navy/orange, a compact score context, a shared
zone, a stable primary action, and collapsed secondary detail. Mobile controls
stay reachable. Routine copy names the action instead of explaining infrastructure.

## Data And Contract Changes

- New `prepared-replay-v1` edition and versioned session records in the `REPLAY#`
  DynamoDB namespace or the new `replay_records` PostgreSQL table.
- New routes: `/api/replays`, `/api/replays/[id]`. Old timeline/job/game routes
  are removed. Existing anonymous cookies remain valid; old timelines do not
  migrate into the new at-bat experience.
- Prediction responses add sample size, pitch-probability provenance, and
  aggregate velocity estimates. They remove fabricated PA forecast/remaining
  pitch fields. Foul tips and bunt fouls have explicit result types.
- No durable legacy records or tables are deleted. The additive SQL migration
  is `packages/db/drizzle/0003_majestic_cerebro.sql`.
- Coordinate-derived location labels are a display projection. Saved model
  requests and responses remain available for provenance.

## First Production Cutover

When replacing the legacy per-click runtime, a reviewed edition produced by the
updated real local model can bootstrap the web cutover. Publish that exact JSON
to DynamoDB, deploy the prepared-replay web runtime, then update the model and
publish an edition generated by its immutable AWS version. This keeps the old
web runtime paired with its old model contract until the web switch. The new
web runtime is independent of the model deployment. Preserve both original
images and stack templates before beginning.

1. Run the complete verification path in `docs/approach.md`. Preserve the current
   web image, model image/version, CloudFormation template, and featured pointer
   if one exists. Do not delete rollback images as part of this release.
2. Deploy the updated model contract with `scripts/deploy-serverless-model.sh`.
   Use an immutable published version for preparation, rather than an alias that
   can move during a run. Verify real inference and the returned contract.
3. For PostgreSQL, run the additive migration with the target database URL.
   DynamoDB requires no table migration and keeps existing keys intact.
4. Prepare a real edition with the updated operator CLI. Use durable storage
   when model calls are billable so budget and checkpoint records survive local
   loss. `prepare:replay --publish` prepares and publishes in one operator run;
   alternatively review a local output and publish that exact JSON with
   `publish:replay --input`.
5. Confirm `STORAGE_MODE=dynamodb DYNAMODB_TABLE_NAME=... npm run publish:replay
-- --check` succeeds. The web deploy script performs this preflight before
   building or modifying the web deployment.
6. Deploy the web stack with `scripts/deploy-serverless-web.sh`. This removes
   model/self-invocation permission and obsolete public model/job configuration,
   sets a 30-second web timeout, and forwards the viewer host for origin checks.
7. Check `/health`, `/ready`, and `BASE_URL=https://baseball.saulrichardson.io npm
run verify:product`. Inspect the actual browser at phone and laptop sizes;
   complete the at-bat, revisit a forecast, refresh, and retry an interrupted
   action. Confirm CloudWatch errors remain clear and contain no secrets.
8. Verify a second browser owns an independent cursor and that old sessions can
   open a new replay. Measure deployed command latency separately from local
   measurements. Inspect model invocations to confirm replay traffic causes none.

The GitHub deployment workflow follows model deployment → durable preparation
and publication → web deployment → readiness/product verification. The first
cutover assumes the existing retained state table; provisioning a brand-new
account/table is a separate infrastructure bootstrap.

## Rollback And Recovery

A failed new preparation does not replace the featured edition. Retry with the
same immutable artifact identity to reuse completed forecasts. Never increase a
model budget to hide an unexplained repeated failure.

To revert the featured replay, use `publish:replay --edition <previous-id>`.
Active sessions continue on their pinned edition either way.

If the web release fails, restore the prior web image **and its prior stack
configuration/IAM**, because the old web app requires model and self-invocation
permissions. Restore the matching model version/alias before sending old-runtime
traffic to it. New replay records coexist with old timeline records, so no data
rollback is required. Keep the existing session secret.

An interrupted local publisher may leave `.cache/replay-preparation/publisher.lock`.
Confirm no local preparation process is running before removing that specific
lock. Durable preparation leases expire after ten minutes; successful forecasts
are retained for retry. The publication step validates the saved complete edition
again before switching the pointer.
